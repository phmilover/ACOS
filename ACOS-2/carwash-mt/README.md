# Автомойка MT (вариант 43)

Многопоточная (pthreads) имитация автоматической автомойки на C17: libc, системные вызовы и
pthread. Поток на каждую машину, каждый пост и координатора; их ходом управляют виртуальные
часы. Последовательная версия - `ACOS-1/carwash`.

Проверено только на macOS (Apple clang 21). Код для Linux предусмотрен (`_DEFAULT_SOURCE`,
`gettid`), но там не собирался и не запускался; GCC не пробовали.

## Сборка и запуск

Все команды - из папки `carwash-mt`.

```bash
cmake -S . -B build && cmake --build build
./bin/carwash-mt                         # обычный день, живая схема с панелью потоков
./bin/carwash-mt -c data/rush-hour.cfg   # другой сценарий
./bin/carwash-mt -m log -s 42            # лента событий, повторяемый прогон
./bin/carwash-mt -m log -s 42 -D         # детерминированный режим: журнал побайтно одинаков
./bin/carwash-mt -u                      # без конца дня, остановка по Ctrl+C
./bin/carwash-mt -h                      # все ключи
```

| Ключ | Что делает |
|---|---|
| `-c FILE` | файл конфигурации (пример формата - `data/normal.cfg`) |
| `-s SEED` | seed генератора |
| `-d MS` | задержка на одну минуту модели, мс (по умолчанию 150 в живой схеме, 0 в ленте) |
| `-m live\|log` | живая схема или лента событий |
| `-l FILE` | журнал, по умолчанию `carwash.log` |
| `-u` | без ограничения времени и числа машин |
| `-i` | ввести основные параметры с клавиатуры |
| `-x overflow\|race\|deadlock` | специально внести ошибку, чтобы проверки её поймали |
| `-D` | детерминированный режим: работает один поток модели за раз |
| `-t` | показывать, какой поток сообщил о событии (`car #3`, `post tunnel.1`, `coordinator`, `clock`) |
| `-g FILE` | при тупике сохранить граф ожидания в формате DOT |

Сигналы (их забирает отдельный поток через `sigwait`, обработчиков нет):

| Сигнал | Что происходит |
|---|---|
| `SIGINT`, `SIGTERM` | прервать: итоги и журнал сохраняются, код выхода 3 |
| `SIGUSR1` | в stderr граф ожидания и таблица потоков, работа продолжается |
| `SIGUSR2` | закрыть въезд досрочно, домыть принятых и выйти с кодом 0 |

Сигналы блокируются после вопросов `-i`, поэтому Ctrl+C на вопросе просто завершает программу.
`SIGPIPE` игнорируется: `./bin/carwash-mt -m log | head` не убивает процесс, запись в закрытый
канал возвращает ошибку, а журнал и код выхода остаются прежними.

Коды выхода: `0` - всё вымыто, `1` - плохие параметры, `2` - тупик, `3` - прервали сигналом,
`4` - сработала проверка: нарушен инвариант (аудитор), порядок блокировок (LOCKDEP) или
SOFT_ASSERT, `5` - не хватило ресурсов (память, поток, семафор). Фатальный LOCKDEP (код 4) и
нехватка памяти (код 5) выходят сразу из того потока, где случились (`_exit` после сообщения в
stderr): итоги и конец журнала в этом случае не печатаются, в живой схеме курсор и цвета
терминала возвращаются.

## Что где лежит

```
include/   заголовки (описания в Doxygen-комментариях)
src/       реализация
  sim.c quiesce.c       виртуальные часы, парковка потоков; крючок «момент покоя»
  line.c stage.c        линия, стадии, «эстафета» мест (бронь, раздача)
  car.c post.c coordinator.c   потоки машины, поста и координатора
  mutex.c sem.c         мьютекс с рангом и LOCKDEP; обёртка над семафорами POSIX
  events.c              шина событий; на неё подписаны:
    view_log.c view_live.c auditor.c gantt.c stats.c snapshot.c
  render.c              поток отрисовки живой схемы (два буфера по кругу, семафоры free/ready)
  signals.c             поток sigwait
  waitgraph.c           граф ожидания при тупике и по SIGUSR1
  config.c rng.c soft_assert.c
  main.c                ключи, запуск и сбор потоков
data/      сценарии
tests/     unit_tests.c - модульные, run_tests.c - сценарные (fork/exec)
scripts/   run_all.sh, stress.sh, demo.sh
docs/      threads.dox (схемы потоков), demo/ (вывод запусков для отчёта)
```

Модель ничего не печатает сама, она шлёт события в шину. Лог, живая схема, аудитор,
диаграмма Ганта и статистика на них подписаны.

## Потоки и синхронизация

```
main ──create/join──► clock   (SimClockMain: виртуальные часы)
  │ ──────────────────► coordinator ──create/join──► car #1 ... car #N
  │ ──────────────────► post ×(число постов всех стадий)
  │ ──────────────────► signals (sigwait)        render (кадры живой схемы)

будят (SimWake / SimKick):
  post ──конец операции, починился──► car          car ──место освободилось──► car
  car ──последняя машина дня──► coordinator        signals ──SimKick──► clock
  clock ──момент покоя: запуск спящих и ожидающих──► любой поток модели
  clock ──RenderSubmit(снимок)──► render
```

**Виртуальные часы.** Каждый поток модели либо работает, либо припаркован (спит до минуты
`SimSleep` или ждёт другого потока `SimPark`). Часы двигают стрелку, только когда никто не
работает и запускать некого (момент покоя). Тогда они вызывают крючок (`quiesce.c`): снимок для
живой схемы, выборка для Ганта, обработка сигналов, поиск тупика. Тот, кто будит поток, сам
увеличивает счётчик работающих до `sem_post`, поэтому часы не проскакивают; если поток
разбудили, пока он ещё работает, пробуждение запоминается (не теряется).

```
SemWait(часы) ─► покой? ─нет─► снова ждать
                   │да
                   ▼
              крючок (снимок, Гант, сигналы, тупик) ─► остановить? ─да─► SimStop
                                                          │нет
                                                          ▼
                          now = ближайшее пробуждение, запуск спящих ─► потоки работают
                                                          ▲                 │
                                  последний запарковался: SemPost(часы) ◄────┘
```

**Передача эстафеты** (`stage.c`). Машина бронирует место на следующей стадии, затем без
вложенных мьютексов освобождает текущее и занимает забронированное. Тот, кто освободил место,
под мьютексом стадии сам решает, кому оно достанется (`StageDispatch`), меняет состояние за
выбранного и будит его. Поэтому приоритет соблюдается точно, а не «как разбудит ОС».

```
машина A закончила ─► StageAdmit(следующая стадия) ──нет места──► в список ожидающих, SimPark
                            │есть                                         ▲
                            ▼                                    будит тот, кто освободил место
            StageVacate(текущая) ─► StageDispatch(текущая): место - следующему, SimWake(B)
                            ▼
            StageCommit(следующая): EV_MOVE, EV_ENTER или EV_QUEUE
```

Какой мьютекс что защищает: стадия (очередь, посты, ожидающие) - мьютекс стадии
(`RANK_STAGE`, они не вкладываются друг в друга); счётчики - `counters`; реестр машин -
`registry`; часы - свой; шина событий и вывод - свои. Те же схемы, красивее, есть в Doxygen
(страница «Потоки и синхронизация», нужен Graphviz).

## Проверки

- **SOFT_ASSERT** (`include/soft_assert.h`) - мягкая проверка предусловий: не роняет программу,
  а пишет условие, файл и строку в stderr; в конце счётчик срабатываний, код выхода 4. При
  `-DNDEBUG` отключена, поэтому санитайзерные сборки делаются в Debug.
- **TSA** (Thread Safety Analysis, `include/tsa.h`) - компилятор не даёт тронуть поле с
  `GUARDED_BY` без захвата мьютекса. Apple clang 21 не умеет связывать `GUARDED_BY` поля
  структуры с соседним полем-мьютексом (на каждый доступ ложное «requires holding mutex»), поэтому
  под ним такая пометка (`MEMBER_GUARDED_BY`) пустая, а `REQUIRES` у функций работает. Поля
  по-настоящему проверяет clang из Homebrew: цель `tsa` (clang-tidy тоже его использует).
- **LOCKDEP** (`mutex.c`) - у мьютексов есть ранги (стадия 10 < линия 20 < реестр 30 < часы 40 <
  шина 50 < вывод 60; поток отрисовки мьютексов не берёт, только семафоры); захват мьютекса с
  рангом не выше уже удерживаемого - ошибка `LOCKDEP:` и сразу `_exit(4)`. Счётчик захваченных
  мьютексов LOCKDEP заодно даёт SOFT_ASSERT «не парковаться с захваченным мьютексом» в `SimSleep`,
  `SimPark`, `SimBegin` (это SOFT_ASSERT, а не LOCKDEP: сообщение `soft assert failed`, код 4 в
  конце прогона).
- **TSan** - цель `tsan`: unit-тесты и сценарные тесты под ThreadSanitizer, `halt_on_error=1`.
  Тест саботажа `-x race` проходит только на сборке `-tsan`. На macOS TSan не видит связи
  `sem_post` -> `sem_wait` именованных семафоров, `sem.c` в сборке с TSan сообщает её вручную.
- **ASan + UBSan** - цель `asan`. LeakSanitizer на macOS не поддерживается
  (`detect_leaks is not supported on this platform`), поэтому там прогон идёт с `detect_leaks=0`;
  на Linux цель включает `detect_leaks=1`.
- **Аудитор** (`auditor.c`) восстанавливает линию только по событиям и после каждого события
  проверяет инварианты I1-I5 (ёмкость поста, одно место у машины, порядок стадий, сломанный пост
  не начинает операцию, очередь не переполнена); итог - в конце вывода.
- **Саботаж** `-x`: `overflow` - ошибки на единицу: лишнее место в очереди и не тот предел цикла
  поиска поста (у стадии с двумя постами ищется один), поэтому очередь переполняется на любом
  seed встроенной конфигурации (ловят аудитор, I5, и SOFT_ASSERT); `deadlock` - переезд «под
  одним замком»: мьютекс следующей стадии берётся, пока текущая захвачена, - ловит LOCKDEP на
  первом же переезде любой машины, до настоящей взаимной блокировки; `race` - инкремент без
  мьютекса (ловит только TSan: на обычной сборке программа пишет об этом в stderr). Примеры
  вывода - `docs/demo/sabotage-*.txt`.
- **Стресс** - `scripts/stress.sh`: сотни прогонов (9 сценариев x seed) без `-D` (`run_all.sh`
  гоняет его и на сборке `-tsan`, 100 прогонов); провал при
  неверном коде выхода, нарушении инварианта, SOFT_ASSERT, LOCKDEP, отчёте TSan или зависании
  дольше 10 с.

## Инструменты

```bash
cmake --build build --target check      # unit_tests, затем сценарные тесты
cmake --build build --target tsan       # build-tsan + тесты под ThreadSanitizer
cmake --build build --target asan       # build-asan + тесты под ASan/UBSan
cmake --build build --target tsa        # build-tsa: Homebrew clang, -Wthread-safety -Werror
cmake --build build --target stress     # 500 прогонов, сводка
cmake --build build --target format     # clang-format
cmake --build build --target tidy       # clang-tidy (в т. ч. concurrency-*)
cmake --build build --target cppcheck   # cppcheck
cmake --build build --target coverage   # build-cov, отчёт llvm-cov: build-cov/html/index.html
cmake --build build --target docs       # Doxygen: build/doxygen/html/index.html
scripts/run_all.sh                      # всё подряд, итоговая таблица PASS/FAIL/SKIP
scripts/demo.sh                         # запуски для отчёта: docs/demo/*.txt (с ANSI)
```

Установка: `brew install llvm cppcheck graphviz doxygen`. Homebrew llvm не попадает в PATH, CMake
находит его в `/opt/homebrew/opt/llvm/bin`. Покрытие считается через `xcrun llvm-profdata` и
`xcrun llvm-cov` (того же выпуска, что Apple clang). Если инструмента нет, цель пишет, что
поставить; `run_all.sh` в таком случае пишет `SKIP` с причиной. Doxygen находит Graphviz сам
(`HAVE_DOT` включается из CMake), без него схемы потоков на странице не рисуются - они остались
выше в этом файле.

Сценарные тесты запускают `bin/carwash-mt` на файлах из `data/` и проверяют код выхода и вывод;
запуск вручную: `./bin/run_tests ./bin/carwash-mt` (для теста гонки - `./bin/carwash-mt-tsan`).

## Ограничения

- Всё проверено только на macOS (Apple clang 21, arm64). Для Linux в CMake добавлен
  `_DEFAULT_SOURCE`, а `src/sim.c` берёт номер потока через `syscall(SYS_gettid)`, но сборка и
  тесты на Linux не запускались.
- TSA для полей структур (`MEMBER_GUARDED_BY`) под Apple clang отключена, полноценная проверка -
  цель `tsa` с clang из Homebrew.
- LeakSanitizer на macOS недоступен, утечки памяти не проверяются; ASan ловит остальные ошибки
  работы с памятью.
