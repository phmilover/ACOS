# Автомойка MON (вариант 43)

Многопоточная (pthreads) имитация автоматической автомойки на C17: libc, системные вызовы и
pthread. Это вторая программа второго индивидуального задания: та же модель, что в
`ACOS-2/carwash-mt`, но потоки взаимодействуют без единого семафора - только мониторами
(мьютекс и условные переменные), `pthread_rwlock`, барьером старта и атомарными операциями C11.
Поток на каждую машину, каждый пост и координатора; их ходом управляют виртуальные часы.
Последовательная версия - `ACOS-1/carwash`.

Проверено только на macOS (Apple clang 21). Код для Linux предусмотрен (`_DEFAULT_SOURCE`,
`gettid`), но там не собирался и не запускался; GCC не пробовали. Ветка `pthread_barrier_*`
на macOS не компилируется (там своя реализация барьера), поэтому не проверена вовсе.

## Сборка и запуск

Все команды - из папки `carwash-mon`.

```bash
cmake -S . -B build && cmake --build build
./bin/carwash-mon                         # обычный день, живая схема с панелью потоков
./bin/carwash-mon -c data/rush-hour.cfg   # другой сценарий
./bin/carwash-mon -m log -s 42            # лента событий, повторяемый прогон
./bin/carwash-mon -m log -s 42 -D         # детерминированный режим: журнал побайтно одинаков
./bin/carwash-mon -u                      # без конца дня, остановка по Ctrl+C
./bin/carwash-mon -h                      # все ключи
```

| Ключ | Что делает |
|---|---|
| `-c FILE` | файл конфигурации (пример формата - `data/normal.cfg`) |
| `-s SEED` | seed генератора |
| `-d MS` | задержка на одну минуту модели, мс (по умолчанию 150 в живой схеме, 0 в ленте) |
| `-m live\|log` | живая схема или лента событий |
| `-l FILE` | журнал, по умолчанию `carwash.log` |
| `-u` | без ограничения времени и числа машин |
| `-i` | ввести основные параметры с клавиатуры |
| `-x overflow\|race\|deadlock` | специально внести ошибку, чтобы проверки её поймали |
| `-D` | детерминированный режим: работает один поток модели за раз |
| `-t` | показывать, какой поток сообщил о событии (`car #3`, `post tunnel.1`, `coordinator`, `clock`) |
| `-g FILE` | при тупике сохранить граф ожидания в формате DOT |

Сигналы (их забирает отдельный поток через `sigwait`, обработчиков нет):

| Сигнал | Что происходит |
|---|---|
| `SIGINT`, `SIGTERM` | прервать: итоги и журнал сохраняются, код выхода 3 |
| `SIGUSR1` | в stderr граф ожидания и таблица потоков, работа продолжается |
| `SIGUSR2` | закрыть въезд досрочно, домыть принятых и выйти с кодом 0 |

Сигналы блокируются после вопросов `-i`, поэтому Ctrl+C на вопросе просто завершает программу.
`SIGPIPE` игнорируется: `./bin/carwash-mon -m log | head` не убивает процесс.

Коды выхода: `0` - всё вымыто, `1` - плохие параметры, `2` - тупик, `3` - прервали сигналом,
`4` - сработала проверка: нарушен инвариант (аудитор), порядок блокировок (LOCKDEP) или
SOFT_ASSERT, `5` - не хватило ресурсов (память, поток, условная переменная). Фатальный LOCKDEP
(код 4), нехватка памяти (код 5) и не созданный участник барьера старта (код 5) выходят сразу:
итоги и конец журнала в этом случае не печатаются.

## Что где лежит

```
include/   заголовки (описания в Doxygen-комментариях)
src/       реализация
  sync.c                мьютекс, условная переменная и rwlock с рангом и LOCKDEP
  barrier.c thread.c    барьер старта; создание потоков (крючок отказа для тестов)
  sim.c quiesce.c       виртуальные часы - монитор; крючок «момент покоя»
  line.c stage.c        линия, монитор стадии (бронь, переезд, условные пробуждения)
  car.c post.c coordinator.c   потоки машины, поста и координатора
  events.c              шина событий; на неё подписаны:
    view_log.c view_live.c auditor.c gantt.c stats.c snapshot.c
  render.c              поток отрисовки живой схемы (ограниченный буфер на условных переменных)
  signals.c             поток sigwait
  waitgraph.c           граф ожидания при тупике и по SIGUSR1
  config.c rng.c soft_assert.c
  main.c                ключи, запуск и сбор потоков
data/      сценарии
tests/     unit_tests.c - модульные, run_tests.c - сценарные (fork/exec)
scripts/   run_all.sh, stress.sh, demo.sh
docs/      threads.dox (схемы потоков), demo/ (вывод запусков для отчёта)
```

Модель ничего не печатает сама, она шлёт события в шину. Лог, живая схема, аудитор,
диаграмма Ганта и статистика на них подписаны.

## Потоки и синхронизация

```
main ──create/join──► signals (sigwait)   render (кадры живой схемы)
  │ ──────────────────► post ×(число постов всех стадий)
  │ ──────────────────► coordinator ──create/join──► car #1 ... car #N
  │ ──────────────────► clock   (SimClockMain: виртуальные часы)
  └─ барьер старта: посты + координатор + часы + main (9 участников на встроенной конфигурации)

будят (SimGrant + CondBroadcast под мьютексом стадии):
  post ──done: конец операции──► car      car/post ──seatFree, room: место──► car
  car ──decided: последняя машина дня──► coordinator
  signals ──SimKick──► clock     clock ──личная cv: запуск──► поток модели
  clock ──RenderSubmit(снимок)──► render
```

**Виртуальные часы** (`sim.c`) - монитор. Каждый поток модели либо работает, либо ждёт (спит до
минуты `SimSleep` или ждёт условия монитора `SimWaitOn`). Часы ждут на условной переменной
`quiet`, пока никто не работает и запускать некого (момент покоя), затем вызывают крючок
(`quiesce.c`): снимок для живой схемы, выборка для Ганта, сигналы, поиск тупика. Тот, кто
разрешает потоку выйти из ожидания (`SimGrant`), сам увеличивает счётчик работающих, поэтому
часы не проскакивают.

**Монитор стадии** (`stage.c`). Мьютекс стадии защищает очередь, посты и список ожидающих;
условные переменные `seatFree` (машины очереди ждут места на посту), `room` (машины других
стадий ждут места) и `done` у каждого поста (конец операции) работают с этим мьютексом.
Освободивший место не выбирает следующего: он будит ждущих, а каждый в цикле `while` проверяет
свой предикат «моя ли очередь» (`StageQueueTurn`, `StageRoomTurn`).

**Барьер старта** (`barrier.h`). Участников: посты + координатор + часы + main (на встроенной
конфигурации 9; число и реализация печатаются в итогах строкой `Threads`). На macOS
`pthread_barrier_t` нет, поэтому барьер собран на мьютексе и условной переменной
(`BarrierKind()` возвращает `mutex+cond`; при `_POSIX_BARRIERS > 0` вне macOS используется
`pthread_barrier_t`). Если участник барьера не создался, дождаться его некому: `main` печатает
причину (`not enough resources: cannot create a thread`) и выходит с кодом 5 без итогов - барьер
нельзя отпустить без всех участников. Поток сигналов создаётся раньше участников барьера, ему
барьер не нужен.

Какой замок что защищает (ранги LOCKDEP): стадия `RANK_STAGE`=10 (мьютексы стадий не
вкладываются) < вход `RANK_ENTRANCE`=20 (координатор и последняя машина дня) < реестр машин
`RANK_REGISTRY`=30 (rwlock) < часы `RANK_SIM`=40 < буфер кадров `RANK_RENDER`=45 < шина событий
`RANK_BUS`=50 < вывод `RANK_OUT`=60. Счётчики линии - атомики. Те же схемы, красивее, есть в
Doxygen (страница «Потоки и синхронизация», нужен Graphviz).

### Подробности, которые не очевидны из кода

- **Ожидающие места** встают в порядке постановки: номер `ticket` - уникальный глобальный
  счётчик `nextTicket` (как в `carwash-mt`). Машина с улицы получает отказ, если кто-то ждёт
  места, даже когда место только что освободилось и разбуженный ожидающий его ещё не занял
  (в обычном режиме это короткое окно; как в `carwash-mt`).
- **Пробуждения условные**: освободивший место будит ждущих условия, только если очередь хотя
  бы одного из них действительно настала (есть свободное место для его предиката), - вхолостую
  `broadcast` не зовут. Но если предикат хоть одного истинен, выход разрешают всем ждущим этого
  условия, и каждый перепроверяет предикат в цикле `while` (не его очередь - снова спит).
- **`CARWASH_FAIL_THREAD_AFTER=N`** (тесты) заставляет `ThreadCreate` с номером N (с нуля) и
  все следующие вернуть `EAGAIN`. Нумерация по порядку создания: `0` - поток сигналов;
  в живой схеме `1` - поток отрисовки; затем участники барьера - посты по стадиям, координатор,
  часы (в ленте событий они идут с `1`); затем потоки машин. На `normal.cfg` в ленте: 1-6 посты,
  7 координатор, 8 часы, 9... машины.
- **`-D` повторяет журнал побайтно только внутри `carwash-mon`.** Журналы `carwash-mon` и
  `carwash-mt` для одного seed различаются: в mon машина из очереди сама садится на пост, когда
  настаёт её очередь, а в mt её сажает освобождающая машина. Задание это допускает.

## Чем отличается от carwash-mt

| Место | В carwash-mt | В carwash-mon | Почему |
|---|---|---|---|
| Парковка машин и постов | личный семафор потока (`SimPark`/`SimWake`) | ждёт на условной переменной стадии (`seatFree`, `room`, `done`), сон и жетон `-D` - на личной условной переменной часов | монитор: условие и данные под одним мьютексом, ожидание атомарно отпускает его |
| Выбор следующего | эстафета: освободивший место решает и меняет состояние за выбранного | освободивший будит ждущих, каждый в `while` проверяет «моя ли очередь» | без семафоров нет адресного «пуска» одного потока; предикат заменяет решение |
| Пробуждение часов | семафор часов | условная переменная `quiet` под мьютексом часов | тот же смысл, ожидание с проверкой условия |
| Кадры отрисовки | два семафора free/ready | ограниченный буфер: `notFull`, `notEmpty`, `drained` под одним мьютексом | классический монитор «производитель-потребитель» |
| Счётчики линии | под мьютексом `counters` | атомики C11 | отдельные независимые числа, замок не нужен |
| Реестр машин | мьютекс | `pthread_rwlock` | пишет один координатор, читают многие (соседи по очереди при каждой проверке) |
| Старт | потоки запускаются по одному | барьер: посты, координатор, часы и main стартуют вместе | порядок создания не влияет на ход |
| Координатор и последняя машина | `SimPark`/`SimWake` | монитор `entrance` (мьютекс + `decided`) | ожидание условия «все решили» |

**Плюсы монитора.** Нет потерянных пробуждений: условие проверяется под тем же мьютексом, под
которым меняется; ложные пробуждения безвредны из-за `while`; код ожидающего читается как
«жду, пока истинно». Приоритет соблюдается через предикат, а не через чей-то выбор.

**Минусы.** `broadcast` будит всех ждущих условия, а проходит один: лишние пробуждения и
повторные проверки предиката (в `carwash-mt` эстафета будит ровно одного). Чтобы это смягчить,
будят только когда предикат хоть у одного ждущего стал истинным. Предикат "чья очередь"
пересчитывается каждым ждущим (берёт соседей через `LineCar` под `rwlock` на чтение).

## Проверки

- **Нет семафоров**: цель `nosem` ищет в `src`, `include`, `tests` следы семафоров (`sem_`,
  `semaphore.h`, `dispatch_semaphore`, `Sem...`) и входит в `check`.
- **SOFT_ASSERT** (`include/soft_assert.h`) - мягкая проверка предусловий: пишет условие, файл и
  строку в stderr; в конце счётчик срабатываний, код выхода 4. При `-DNDEBUG` отключена,
  поэтому санитайзерные сборки делаются в Debug.
- **TSA** (Thread Safety Analysis, `include/tsa.h`) - компилятор не даёт тронуть поле с
  `GUARDED_BY` без захвата мьютекса. Apple clang 21 не умеет связывать `GUARDED_BY` поля
  структуры с соседним полем-мьютексом, поэтому под ним такая пометка (`MEMBER_GUARDED_BY`)
  пустая, а `REQUIRES` у функций работает. Поля проверяет clang из Homebrew: цель `tsa`.
- **LOCKDEP** (`sync.c`) - у мьютексов и rwlock есть ранги (см. выше); захват с рангом не выше
  уже удерживаемого - ошибка `LOCKDEP:` и сразу `_exit(4)`. Счётчик захваченных замков даёт
  SOFT_ASSERT «не спать и не начинать с захваченной блокировкой» (`SimSleep`, `SimBegin`,
  в `SimWaitOn` - ровно один замок, тот, с которым ждёт).
- **TSan** - цель `tsan`: unit-тесты и сценарные тесты под ThreadSanitizer, `halt_on_error=1`.
  Тест саботажа `-x race` проходит только на сборке `-tsan`.
- **ASan + UBSan** - цель `asan`. LeakSanitizer на macOS не поддерживается, поэтому прогон
  идёт с `detect_leaks=0`; на Linux цель включает `detect_leaks=1`.
- **Аудитор** (`auditor.c`) восстанавливает линию только по событиям и после каждого события
  проверяет инварианты I1-I5 (ёмкость поста, одно место у машины, порядок стадий, сломанный пост
  не начинает операцию, очередь не переполнена); итог - в конце вывода.
- **Саботаж** `-x`: `overflow` - ошибки на единицу (лишнее место в очереди, не тот предел
  поиска поста): очередь переполняется на любом seed встроенной конфигурации, ловят аудитор (I5)
  и SOFT_ASSERT; `deadlock` - переезд «под одним замком»: мьютекс следующей стадии берётся, пока
  текущая захвачена, - ловит LOCKDEP на первом же переезде, до настоящей взаимной блокировки;
  `race` - инкремент без мьютекса (ловит только TSan). Примеры - `docs/demo/sabotage-*.txt`.
- **Стресс** - `scripts/stress.sh`: сотни прогонов (9 сценариев x seed) без `-D`; провал при
  неверном коде выхода, нарушении инварианта, SOFT_ASSERT, LOCKDEP, отчёте TSan или зависании
  дольше 10 с. `run_all.sh` гоняет его и на сборке `-tsan`.

## Инструменты

```bash
cmake --build build --target nosem      # в src, include, tests нет семафоров
cmake --build build --target check      # nosem, unit_tests, затем сценарные тесты
cmake --build build --target tsan       # build-tsan + тесты под ThreadSanitizer
cmake --build build --target asan       # build-asan + тесты под ASan/UBSan
cmake --build build --target tsa        # build-tsa: Homebrew clang, -Wthread-safety -Werror
cmake --build build --target stress     # 500 прогонов, сводка
cmake --build build --target format     # clang-format
cmake --build build --target tidy       # clang-tidy (в т. ч. concurrency-*)
cmake --build build --target cppcheck   # cppcheck
cmake --build build --target coverage   # build-cov, отчёт llvm-cov: build-cov/html/index.html
cmake --build build --target docs       # Doxygen: build/doxygen/html/index.html
scripts/run_all.sh                      # всё подряд, итоговая таблица PASS/FAIL/SKIP
scripts/demo.sh                         # запуски для отчёта: docs/demo/*.txt (с ANSI)
```

Установка: `brew install llvm cppcheck graphviz doxygen`. Homebrew llvm не попадает в PATH, CMake
находит его в `/opt/homebrew/opt/llvm/bin`. Покрытие считается через `xcrun llvm-profdata` и
`xcrun llvm-cov`. Если инструмента нет, цель пишет, что поставить; `run_all.sh` в таком случае
пишет `SKIP` с причиной.

Сценарные тесты запускают `bin/carwash-mon` на файлах из `data/` и проверяют код выхода и вывод;
запуск вручную: `./bin/run_tests ./bin/carwash-mon` (для теста гонки - `./bin/carwash-mon-tsan`).

## Ограничения

- Всё проверено только на macOS (Apple clang 21, arm64). Linux/GCC не пробовали; ветка
  `pthread_barrier_*` на macOS не компилируется.
- TSA для полей структур (`MEMBER_GUARDED_BY`) под Apple clang отключена, полноценная проверка -
  цель `tsa` с clang из Homebrew.
- LeakSanitizer на macOS недоступен, утечки памяти не проверяются.
- Журнал `-D` не совпадает с журналом `carwash-mt` для того же seed (см. выше).
